# Method 2: Aksharamukha (External Deterministic Standardized Transliteration)

**Implementation:** `src/transliteration/aksharamukha_method.py`
**Output directory:** `data/romanized/aksharamukha/`
**External dependency:** `aksharamukha==2.3` (pinned in `requirements.txt`)
**Type:** Rule-based, deterministic, third-party library
**Direction:** Sinhala (Unicode) → Romanized Sinhala (ASCII Latin, via ISO-15919-style intermediate)
**License of underlying library:** GNU AGPL-3.0 (this must be disclosed if the tool or its output is redistributed; check your paper/repo's license compatibility)

## 1. Purpose and role in the study

Aksharamukha is a general-purpose, actively maintained, peer-adopted Indic script transliteration engine that supports Sinhala among ~120 scripts. It is not written for this project and is not tuned to Sinhala MMLU/SOLD text, which makes it a genuinely **independent external baseline** — useful to argue that observed LLM degradation patterns are not an artifact of one lab's homemade transliterator.

Unlike the in-house `phonetic.py` method, Aksharamukha implements orthographic conventions from the wider Indic-transliteration literature (vowel length marking, standard scholarly diacritics) rather than ad hoc Singlish spelling. This project converts its scholarly ISO output into a documented ASCII projection so it stays comparable to the other three ASCII methods (no diacritics leak into the LLM prompts).

## 2. How it is invoked

```python
from aksharamukha import transliterate as aksharamukha
iso = aksharamukha.process("Sinhala", "ISO", token, nativize=False)
```

- Source script: `"Sinhala"`.
- Target scheme: `"ISO"` — Aksharamukha's implementation of an ISO-15919-style romanization (not necessarily byte-identical to the official ISO 15919:2001 standard's Sinhala tables, since Aksharamukha's ISO scheme is shared across many Brahmic scripts; this should be described in the paper as *"Aksharamukha's ISO transliteration scheme"* rather than *"ISO 15919"* verbatim, to avoid overstating standards compliance).
- `nativize=False`: disables Aksharamukha's optional language-specific "nativization" post-processing, so the output is the direct scheme mapping.

Only Sinhala-block spans (detected via a regex splitting on `\u0d80–\u0dff` plus joiners) are sent to Aksharamukha; everything else (English words, `@mentions`, punctuation, digits) passes through untouched, preserving code-mixed content exactly as written.

## 3. Diacritic-to-ASCII projection (implemented post-processing)

Aksharamukha's raw ISO output uses IPA-adjacent Latin diacritics. This project applies a fixed, documented substitution table, then strips any remaining Unicode combining marks (category `Mn`) via NFD decomposition:

| ISO diacritic form | ASCII projection | Rationale |
|---|---|---|
| `ā` | `aa` | long vowel doubling, matches Singlish convention |
| `ī` | `ii` | ” |
| `ū` | `uu` | ” |
| `ē` | `ee` | ” |
| `ō` | `oo` | ” |
| `æ` | `ae` | short front vowel unique to Sinhala |
| `ǣ` | `aae` | long counterpart |
| `r̥`, `r̥̄` | `ru`, `ruu` | vocalic r (ඍ/ෘ, ඎ/ෲ) |
| `l̥`, `l̥̄` | `lu`, `luu` | vocalic l (ඏ, ඐ/ෳ) |
| `ṁ` | `n` | anusvara |
| `ḥ` | `h` | visarga |
| `ṅ` | `ng` | velar nasal |
| `ñ` | `ny` | palatal nasal |
| `ṭ`, `ḍ`, `ṇ` | `t`, `d`, `n` | retroflex series collapsed to plain letters (same simplification as Method 1) |
| `ś`, `ṣ` | `sh`, `sh` | palatal/retroflex sibilants merged |
| `ḷ` | `l` | retroflex lateral |
| `n̆`, `m̆` | `n`, `m` | prenasalized-consonant diacritic stripped |
| *(any remaining combining mark)* | *(removed)* | NFD decomposition + category-`Mn` filter as a safety net |
| Sinhala `c` (from ISO) | `ch` | matches Singlish spelling of ච |
| Sinhala `v` (from ISO) | `w` | ව is conventionally typed `w` in Singlish, not `v` |

The final two substitutions (`c→ch`, `v→w`) are applied globally to the already-ASCII string as the last step, which is safe because by that point no other source of literal `c` or `v` remains in the Sinhala-derived text.

## 4. Worked examples (generated by the current implementation)

| Sinhala input | Aksharamukha ISO (raw) | Final ASCII output (this method) |
|---|---|---|
| `සිංහල` | `siṁhala` | `sinhala` |
| `වෙසක්` | `vesak` | `wesak` |
| `ප්‍රතිපත්ති` | `pratipatti` | `pratipatti` |
| `කොහොමද?` | `kohomada?` | `kohomada?` |
| `තේ නෙවෙයි තෝ බීලා ඉන්නෙ ගිනි වතුර` | — | `tee neweyi too biilaa inne gini watura` |
| `ශ්‍රී ලංකාව` | `śrī laṁkāva` | `shrii lankaawa` |

Full sentence: `වෙසක් උත්සවයේදී බෞද්ධයින් අනුගමනය කරන පූජා විධි දෙක නම්,` → `wesak utsawayeedii bauddhayin anugamanaya karana puujaa widhi deka nam,`

Compare to Method 1 (`phonetic.py`) on the same sentence: `wesak uthsawayeedii bauddhayin anugamanaya karana puujaa widhi deka nam,` — the only difference is `uthsawayeedii` vs `utsawayeedii` (aspirated-`th` vs plain-`t` spelling of ත/ථ), illustrating that the two rule-based methods largely agree, differing mainly in aspirate-consonant spelling convention.

## 5. Guarantees and validation

Same shared writer and leakage validator as all other methods (see Method 1, §5). Measured on this repository's data (2026-07 run): **1,851** SinhalaMMLU + **2,500** SOLD records processed successfully, **0** Sinhala leakage.

One malformed-input recovery was required during generation: uroman/Aksharamukha runs on this corpus surfaced two Sinhala-side data irregularities (a repeated vowel sign in `mmlu_0875` and a standalone visarga `ඃ` at the end of `sold_0555`) that are properties of the *source corpus*, not this method; both are handled without leaking Sinhala characters into the output.

Throughput: ≈330 strings/second (measured over 11,755 MMLU+SOLD strings, single process, no batching) — this is a Python-to-subprocess/service call for each token internally in Aksharamukha, making it roughly 75× slower than the in-house phonetic method and roughly 3× slower than uroman. This should be reported if runtime/scalability is discussed in the paper; it was not a bottleneck for a one-off corpus preparation step (full MMLU+SOLD generation completes in under a minute), but would matter for real-time use.

## 6. Known limitations (for Discussion/Limitations)

- **Standardized, not colloquial.** Aksharamukha's ISO scheme is built for lossless scholarly script conversion, not for matching how Sri Lankans actually type Singlish on social media (e.g., it will not spontaneously produce common shortenings).
- **Retroflex/dental/sibilant collapsing** in the ASCII projection is this project's own post-processing choice, not a property of Aksharamukha itself — the underlying ISO output does preserve those distinctions (`ṭ` vs `t`, `ś` vs `ṣ`), so a reviewer could reasonably ask for a second "lossless" condition using the raw ISO output; that raw output is available by skipping the ASCII-projection step.
- **AGPL-3.0 license** on the `aksharamukha` PyPI package is a copyleft license; if the transliteration code (not just outputs) is distributed alongside the paper, this should be disclosed.
- **Slower than in-house/uroman methods**, relevant only if runtime is part of the evaluation.
